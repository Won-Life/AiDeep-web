# 그래프 도메인 규칙 (Living Document)

그래프 캔버스의 기능 명세이자 구현 체크리스트. **실제 코드 동작 기준으로 서술한다.**
**구현·수정 작업에서 그래프 동작이 바뀌면 이 문서의 해당 항목을 같은 브랜치에서 함께 갱신한다.**

- `[x]` 구현 완료 / `[ ]` 미구현 / ⚠️ 규칙과 실제 동작이 다르거나 모순 있음 (→ §10)
- 코드 진입점: `src/features/graph/components/GraphCanvas.tsx`
- AI 작업 규칙(패턴·불변식)은 `src/features/graph/CLAUDE.md` 참고 — 이 문서는 "무엇을 해야 하는가 + 실제로 어떻게 동작하는가", CLAUDE.md는 "구현 시 지켜야 할 패턴"
- 핸들 방향(`handleSide`) 체계의 설계 배경은 [AiDeep-web#58](https://github.com/Won-Life/AiDeep-web/pull/58) 참고

## 0. 용어와 기본 구조 (전제)

이 문서 전체가 아래 전제 위에서 서술된다.

1. **그래프** = 엣지로 연결된 노드들의 집합. 한 워크스페이스 캔버스에 여러 그래프가 공존한다.
2. **엣지의 방향이 곧 부모-자식 관계다.** `edge.source` = 부모, `edge.target` = 자식. 부모 판별(`getParentId`)은 "나를 target으로 갖는 엣지의 source"로만 판단하며, 색상·위치는 부모 판별에 쓰지 않는다.
3. **트리 전제**: 모든 노드는 부모(incoming 엣지)를 최대 1개만 가진다 — #92. 그래프의 **루트**는 (a) 메인(PROJECT) 노드이거나 (b) 부모 없는 일반 노드다.
4. **메인 노드**(`data.isMain`, `node_type === 'PROJECT'`): 프로젝트 중심 노드. 연결 시 항상 부모(source)가 되고, 화면에는 흰색으로 표시되지만 내부적으로 그래프 색을 `data.color`에 보유한다.
5. **그래프 소속의 식별자는 색상이다.** 같은 색 = 같은 그래프. 서브트리 순회 자체는 엣지(source→target) 기반 BFS(`getDescendantIds`)이고, 색상은 "어디까지가 내 그래프인가"라는 **경계 판단**에만 쓰인다(`getSameColorDescendantIds`).
6. **그래프 간 엣지**: 서로 다른 그래프(서로 다른 색)의 노드를 잇는 엣지. 일반 부모-자식 엣지와 데이터 구조상 구분이 없다 — 이것이 §10 모순들의 공통 뿌리다.
7. **handleSide**: 자식 노드가 부모의 왼쪽/오른쪽 어느 방향에 붙는지(`'left' | 'right'`). `node.data.handleSide`에 저장되며 엣지의 `sourceHandle`/`targetHandle`과 짝을 이룬다. side가 `right`이면 엣지는 `source-right` → `target-left`로 연결된다(`resolveHandleId`).
8. **동기화**: 본인 변경은 REST 응답 후 로컬 state 반영(낙관적 삽입 없음 — 단 연결 시 색·위치 선반영 예외는 §3-3), 협업자 변경은 WS 이벤트로만 반영.
9. **핸들 제스처와 엣지 레코드는 다른 층위다.** React Flow는 loose 모드(`ConnectionMode.Loose`)이고 모든 target 핸들이 연결 시작 불가(`isConnectableStart={false}`)이므로, 연결 드래그는 **source 핸들에서만 시작**할 수 있고 상대의 source·target 어느 핸들에나 드롭할 수 있다 — 즉 source 핸들끼리 잇는 제스처도 허용된다. 반면 저장되는 엣지 레코드의 `sourceHandle`/`targetHandle` 필드는 "부모의 바깥 방향 핸들 → 자식의 부모 방향 핸들"이라는 의미로 고정되어 있어서, 연결 확정 시(`onConnect`) 부모/자식을 정한 뒤 실제 드롭 지점과 무관하게 필드를 `source-*` / `target-*` 쌍으로 **다시 써서 저장**한다(정규화). 이 재라벨링이 시각적으로 문제없는 이유는, 현재 허용되는 연결에서 자식이 되는 쪽이 항상 부모 없는 노드이고 부모 없는 노드는 source 핸들과 같은 자리에 숨김 target 핸들을 함께 렌더링하기 때문이다(§4). **양쪽 다 부모가 있는 노드끼리의 연결에서는 이 정규화가 성립하지 않는다** (§10-1).

## 2. 노드 생성 (4경로)

모든 경로가 `createMdNode` REST POST → 응답의 `nodeId`로 로컬 삽입. 낙관적 삽입 없음, 실패 시 노드 미생성.

| 경로 | 트리거 | 연결 | 색상 |
|------|--------|------|------|
| 빈 화면 클릭 (`onPaneClick`) | 캔버스 빈 공간 클릭 | 없음 (독립 노드) | 랜덤 색 |
| 핸들 드래그 → 빈 공간 드롭 (`onConnectEnd`) | 핸들에서 뽑은 엣지를 빈 공간에 놓음 | 시작 노드 → 새 노드 (§3-4) | 시작 노드 그래프 색 |
| 리소스 드롭 — 노드 근처 (`onDrop`) | 사이드바 리소스를 노드 50px 이내에 드롭 | hover 노드 → 새 노드 | hover 노드 그래프 색 |
| 리소스 드롭 — 빈 공간 (`onDrop`) | 사이드바 리소스를 빈 공간에 드롭 | 없음 (독립 노드) | 기본 회색 |

- [x] 핸들 드래그 생성 시, 자동 배치 결과 위치에 이미 다른 노드가 있으면 **노드·연결 모두 생성하지 않음**
- [x] 연결 드래그 직후 발생하는 pane 클릭은 노드 생성으로 이어지지 않음 (`isConnectingRef`)
- [x] 다중 선택 해제를 위한 빈 공간 클릭은 노드를 생성하지 않음

## 3. 연결 생성 (4경로)

연결이 만들어지는 경로는 네 가지이며, **경로마다 부모 결정·검사 규칙이 다르다.**

| # | 경로 | 트리거 | 상세 |
|---|------|--------|------|
| 1 | 핸들 드래그 — 기존 노드 연결 | 핸들에서 엣지를 뽑아 다른 노드에 드롭 | §3-3 |
| 2 | 핸들 드래그 — 새 노드 생성 | 핸들에서 엣지를 뽑아 빈 공간에 드롭 | §3-4 |
| 3 | 노드 드래그 편입 | 노드를 다른 노드 근처(50px)에 드래그해 놓음 | §3-5 |
| 4 | 리소스 드롭 | 사이드바 리소스를 노드 근처(50px)에 드롭 | §3-6 |

§3-1·§3-2는 연결 확정 전에 거치는 **공통 점검 규칙**(방향 결정·연결 제한 — 단 경로별 적용 범위가 다름 ⚠️), §3-3~§3-6은 **경로별 동작**이다.

### 공통 점검 규칙

#### 3-1. 부모/자식 방향 결정 — 핸들 드래그 경로 (`resolveConnectionDirection`)

핸들 드래그 A→B는 기본적으로 A=부모(source), B=자식(target)이다. 아래 경우에만 방향을 뒤집는다(swap):

1. **메인 노드는 항상 부모** — 메인 노드가 드래그의 도착점(B)이어도 메인이 source가 된다
2. **단독 노드(엣지 0개)가 그래프에 연결되면 그래프 쪽이 부모** — 단독 노드가 드래그를 시작했어도 그래프에 편입되는 자식이 된다

`onConnect`(연결 확정)와 `isValidConnection`(드래그 중 유효성 표시)이 같은 헬퍼를 공유한다 — 검사와 실제 연결의 방향 판단이 어긋나지 않게 하기 위함.

#### 3-2. 연결 제한 (경로별로 적용 범위가 다름 ⚠️)

**핸들 드래그(`isValidConnection` + `onConnect`)에서 차단되는 것:**

- [x] 자기 자신과 연결
- [x] 메인 노드 ↔ 메인 노드
- [x] 직접 부모-자식 재연결 (이미 연결된 쌍)
- [x] **같은 메인 그래프에 속한 노드끼리** (메인 ↔ 서브 재연결 방지 — 조상·형제도 이 검사로 차단됨)
- [x] **단일 부모 불변식 (#92)**: swap 이후의 실제 자식이 이미 부모를 가지면 차단. `onConnect`에서도 이중 방어 (프로그래매틱 연결 대비)
- [x] **부모가 있는 노드의 부모 방향(`target-*`) 핸들로 들어오는 연결** — 연결은 부모 반대 방향으로만. swap으로 그 노드가 부모가 되는 케이스도 드롭 지점이 부모 방향이면 차단 (부모 없는 노드의 target 핸들 드롭은 허용)

**노드 드래그 편입·리소스 드롭(`isInvalidConnection`만 사용)에서 차단되는 것:**

- [x] 자기 자신 / 메인 ↔ 메인 / 직접 부모-자식
- [x] **순환 차단**: 부모가 될 노드(source)가 이미 자식이 될 노드(target)의 자손이면 차단 — `isInvalidConnection`이 `getDescendantIds(target).has(source)`로 판정. 모든 연결 경로가 이 함수를 거치므로 핸들 드래그·편입·hover 감지가 한 곳에서 막힌다 (§10-4/10-5)
- ⚠️ 같은 그래프 검사·단일 부모 검사는 여전히 **하지 않는다**. 노드 드래그 편입은 기존 부모 엣지를 끊고 재연결(재부모화)하므로 단일 부모는 결과적으로 유지되지만, 조상·형제로의 스냅(재부모화)은 허용된다 (→ §10-4)

참고: 형제·조상 연결 차단은 전용 검사가 아니라 "같은 그래프 검사 + 단일 부모 검사"의 부수 효과로 성립한다 (§10-6).

### 경로별 동작

#### 3-3. 핸들 드래그 — 기존 노드끼리 연결 (`onConnect`)

1. 방향 결정(§3-1) 후 단일 부모·target 핸들 검사(§3-2) 통과 시 진행
2. **양쪽 모두 기존 그래프 소속**(각자 엣지 1개 이상)이면: 색상·위치 모두 유지하고 **연결만 생성** (그래프 간 연결 — 단 현재 도달 가능한 케이스가 제한적, §10-1)
3. 그 외(단독 노드 편입 등): 자식(+그 서브트리)을 부모 기준 자동 배치 위치로 이동시키고, 부모 그래프 색을 자식 서브트리에 전파
4. 자식의 `handleSide` 저장: swap 반영 후 source 쪽 핸들 이름에서 left/right 추출 → 핸들 이름에 방향이 없으면 위치 기반 fallback
5. **서버 반영 순서** ⚠️: 색·위치는 `createEdge` REST **요청 전에** 로컬 선반영(엣지 생성 실패 시 롤백 없음), 엣지 자체는 REST 성공 후에만 로컬 삽입, 색상 저장은 엣지 생성 성공 후 대상 노드별 `updateNodeContent` PATCH

#### 3-4. 핸들 드래그 — 빈 공간 드롭으로 새 노드 생성 (`onConnectEnd`)

노드 생성 자체(REST 순서·겹침 시 미생성)는 §2의 "핸들 드래그 → 빈 공간 드롭" 행과 같은 경로 — 여기서는 연결 관점만 서술한다.

- [x] **부모는 항상 드래그 시작 노드** — 새 노드는 생성 직후라 엣지가 없으므로 방향 swap(§3-1)·연결 제한(§3-2)이 개입할 상황이 없다
- [x] 새 노드는 시작 노드의 그래프 색을 **생성 시점에 부여**받는다 (연결 후 색 전파가 아님)
- [x] side 결정: 메인 그래프 소속이면 루트 반대(바깥) 방향 강제 → 시작 핸들 이름의 left/right → 부모(없으면 메인 노드) 기준 위치 fallback (§4 표와 동일)
- [x] 서버 반영 순서: `createMdNode` 성공 → 노드 로컬 삽입 → `createEdge` 성공 후 엣지 로컬 삽입. 엣지 생성이 실패하면 **그래프 색만 입은 독립 노드가 남는다** (콘솔 로그만, 롤백 없음)

#### 3-5. 노드 드래그 편입 (`onNodeDragStop`, hover-snap)

- [x] 노드 A를 드래그해 노드 B 근처(50px)에 놓으면 연결 생성 — hover 시 B가 커지는 효과
- [x] **부모 결정**: 드래그한 노드가 메인이면 드래그한 쪽이 부모, 그 외에는 **hover된 노드(B)가 항상 부모**
- [x] **재부모화**: 자식(A)에 기존 부모가 있으면 기존 부모 엣지를 로컬·서버 모두 삭제하고 B → A로 재연결
- [x] **side 결정**: 부모가 루트(부모 없음)면 자식의 상대 위치 기반, 부모가 depth>0이면 **부모의 handleSide 계승** (트리가 같은 방향으로 계속 뻗어나가도록)
- [x] 자식(+같은 그래프 서브트리)을 부모 기준 자동 배치 위치로 스냅
- [x] 스냅 후 서브트리 평균 중심이 연결 방향과 반대에 있으면 서브트리를 대칭 이동(§5-2)
- [x] 부모 그래프 색을 자식 서브트리에 전파 (로컬 페인트 + 노드별 PATCH)
- [x] 다중 선택 드래그 중에는 hover-snap 비활성화

#### 3-6. 리소스 드롭 연결 (`onDrop`)

- [x] hover된 노드가 있고 유효하면: 새 노드를 hover 노드의 자식으로 생성 + 연결
- [x] side 결정은 §3-5와 동일 기준: hover 노드에 handleSide가 있으면 계승, 없으면(루트) 드롭 위치 기반

## 4. handleSide (핸들 방향) 규칙 — AiDeep-web#58

핸들 방향은 **위치가 아니라 연결 관계(topology)로 결정**된다. 위치는 드래그 중 계속 바뀌므로 위치 기반 재계산은 엣지 방향이 흔들리는 근본 원인이었음. topology가 바뀌는 시점에만 명시적으로 갱신한다.

| 시점 | handleSide 결정 기준 |
|------|---------------------|
| 마운트 (`initializeHandleSides`) | incoming 엣지의 `sourceHandle`에서 추출 (서버 데이터 기반) |
| 핸들 드래그 연결 (`onConnect`) | swap 반영 후 source 핸들 방향 → 위치 fallback |
| 노드 드래그 편입 (`onNodeDragStop`) | 부모가 루트 → 위치 / depth>0 → 부모 계승 |
| 리소스 드롭 (`onDrop`) | 부모가 루트 → 드롭 위치 / depth>0 → 부모 계승 |
| 핸들 드래그 새 노드 생성 (`onConnectEnd`) | 메인 그래프 소속이면 루트 반대(바깥) 방향 강제 → 핸들 이름 → 위치 |
| 대칭 이동 (§5-2) | 새 side로 일괄 갱신 (⚠️ 로컬만 — §10-3) |
| 단순 위치 이동 | **변경 없음** (갱신하면 DB `sourceHandle`과 불일치 → 새로고침 시 엣지 방향이 튐) |

- [x] 엣지 렌더링(`buildEdgePresentation`)은 `node.data.handleSide`(storedSide)를 최우선 참조 — 드래그 중 position이 바뀌어도 핸들이 흔들리지 않음
- [x] 메인 노드 자신은 handleSide를 갖지 않음 (양방향으로 자식을 가질 수 있으므로)
- [x] **핸들 렌더링 구조** (`src/features/nodes/TextUpdateNode.tsx`) — §0-9 정규화와 §10-1을 이해하는 전제:
    - **부모 없는 노드 = 핸들 4개**: 양쪽에 source 핸들(hover 시에만 표시, 드래그 시작 가능) + 같은 자리에 겹쳐진 숨김 target 핸들(드롭 앵커 전용). 그래서 어느 방향으로든 연결 가능하고, source 핸들에 드롭된 연결을 target 핸들 라벨로 저장해도 같은 위치에 앵커된다
    - **부모 있는 노드 = 핸들 2개뿐**: 부모 방향에 숨김 target 핸들, 부모 반대 방향에 source 핸들. **부모 반대(자유) 방향에는 target 핸들이 없다** — 부모 있는 노드를 target으로 기록한 엣지는 그 노드의 부모 방향에만 앵커할 수 있다
    - 모든 target 핸들은 연결 시작 불가 → 연결 드래그는 항상 source 핸들에서 시작된다

## 5. 노드 이동

### 5-1. 기본 드래그

- [x] 메인 노드 드래그 → 같은 그래프(같은 색) 전체가 함께 이동
- [x] 일반 노드 드래그 → 해당 노드 + 같은 그래프 서브트리가 함께 이동 (그래프 간 엣지 너머의 다른 그래프 노드는 따라오지 않음 — 색 경계)
- [x] 형제 노드가 있어도 선택한 노드(+서브트리)만 이동
- [x] opt/alt + 드래그 → 서브트리를 떼어놓고 드래그한 노드만 단독 이동 (⚠️ 이 상태로 자기 자손 근처에 놓으면 순환 생성 가능 — §10-4)
- [x] 다중 선택 드래그: 선택된 모든 노드 + 각자의 서브트리가 함께 이동 (⚠️ 이 경로만 색 경계를 적용하지 않아 다른 그래프가 딸려감 — §10-8)
- [x] 드래그 중 엣지도 실시간으로 따라 움직임 (허브 이후 평행선이 늘어나는 형태)

### 5-2. 대칭 이동 (mirror)

대칭 이동은 **드래그 중**과 **드래그 종료 시** 두 경로가 있고, 트리거·구현이 다르다 (같은 드래그에서 이중 적용은 없음 — 드래그 중 대칭이 일어난 프레임은 서브트리 delta 추종을 건너뛰고, 두 경로는 발동 조건이 배타적으로 순차 실행됨).

**드래그 중 대칭** — 메인 노드의 직계 자식을 드래그해 메인 노드의 좌우 축을 넘긴 순간:

- [x] 드래그 노드는 마우스를 그대로 따라가고, 서브트리만 드래그 노드 기준 거리를 유지한 채 반대편으로 대칭 이동 — **d3 시뮬레이션 좌표를 직접 변경**하므로 드래그 종료 시 새 위치가 서버에 저장됨
- [x] 드래그 노드 + 서브트리의 handleSide와 관련 엣지의 핸들·허브 좌표를 새 방향으로 일괄 갱신 (⚠️ 엣지 핸들은 로컬만 — 새로고침 시 확정적으로 어긋남, §10-3)
- ⚠️ 메인 노드가 없는 그래프(일반 노드가 루트)에서는 축 판정이 메인 노드 기준이라 **드래그 중 대칭이 아예 동작하지 않음** — #99와 같은 뿌리

**드래그 종료 시 대칭** — 편입 스냅(§3-5) 후 서브트리 평균 중심이 연결 방향 반대에 있으면:

- [x] 서브트리를 새 부모 기준 축으로 대칭 이동 (`mirrorSubtree`)
- [x] 뒤집힌 위치를 d3 좌표(`d3NodesRef`)에도 동기화 → 자손 저장이 보정된 위치로 나감 (§10-7 위치 저장 해결). 중심점 대칭이라 `2*axis - center`로 반영
- [x] 대칭된 자손의 `handleSide`를 새 방향(부모 기준 side)으로 갱신 → 렌더 엣지는 `buildEdgePresentation`이 타깃 노드 handleSide에서 핸들·hub를 재계산하므로(§4) **세션 중 로컬 교차 렌더링은 사라진다**
- ⚠️ 단, 뒤집힌 `sourceHandle`을 **서버에 저장하지 못함**(엣지 PATCH API 부재) → 새로고침하면 마운트 초기화가 DB의 옛 핸들을 읽어 교차 재발 — §10-3 (백엔드 Aideep_backend#56 대기)

**공통**:

- [x] **대칭 이동 시 그래프 간 엣지 절단**: 색이 다른(다른 그래프) 직계 자식은 대칭 이동을 따라오지 않아 연결 방향 규칙이 꼬이므로, 해당 엣지를 로컬·서버 모두 삭제 (드래그 중에도 즉시 DELETE)
- [ ] depth 설정 로직 — #99: 일반 노드 depth 0 기준 대칭 이동 조정 (미구현)

### 5-3. 화면 상 이동 vs 서버 저장 시점

드래그 중 화면의 움직임과 서버 저장은 **완전히 분리**되어 있다:

1. **드래그 중** — 서버 DB에는 아무것도 저장하지 않는다.
   - **위치의 단일 진실은 d3 시뮬레이션 좌표**: 드래그 노드는 마우스 위치가 d3 고정 좌표(fx/fy)로 복사되고, 서브트리는 프레임 delta가 fx/fy에 누적되며, d3 tick이 매 프레임 **캔버스의 모든 노드**를 d3 좌표로 화면(React state)에 일괄 반영 (밀려나는 주변 노드 포함)
   - ⚠️ tick이 드래그 시작 시점 스냅샷 기준으로 전체를 덮어쓰므로, 드래그 중 협업자가 옮긴 노드는 내 화면에서 옛 위치로 되돌아감 — §10-9
   - 협업자 화면 표시용으로 **드래그 노드의 위치만** WS `emitLivePosition`으로 브로드캐스트 (50ms throttle) — 실시간 표시용이며 위치 영속화가 아님. 서브트리 위치는 브로드캐스트되지 않아 협업자에게는 드롭 순간 한 번에 점프해 보임
   - 예외: 대칭 이동으로 절단되는 그래프 간 엣지는 드래그 **중에도** `deleteEdge` REST 즉시 호출
2. **드래그 종료 (`onNodeDragStop`)** — 이 시점에 비로소 REST로 저장한다.
   - 드래그한 노드: `moveNode` PATCH (편입 스냅이 일어났으면 스냅 보정된 위치로)
   - 함께 이동한 같은 그래프 서브트리: 노드별 `moveNode` PATCH — **d3 시뮬레이션 좌표 기준**. 편입 스냅의 위치 보정(스냅 delta·종료 시 대칭)도 d3 좌표에 동기화하므로 보정된 위치가 저장된다 (§10-7). 메인 노드 드래그 편입 시 상대 서브트리는 `incorporatedIds`로 따로 담아 별도 PATCH (§10-7)
   - 다중 선택 드래그: 선택된 노드들 + 각 서브트리도 노드별 PATCH (⚠️ 색 경계 미적용 — §10-8)
   - 시뮬레이션에 **밀려나기만 한** 주변 노드(드래그 대상이 아니었던 노드)의 위치는 저장하지 않는다 ⚠️ → 새로고침 시 밀려난 노드는 원위치로 복귀

## 10. 알려진 모순·규칙-코드 불일치 (미해결)

동작을 바꾸는 결정이 내려지면 해당 섹션과 함께 이 목록을 갱신한다.

### 10-1. ⚠️ "그래프 간 연결" 규칙이 단일 부모 검사(#92)로 사실상 차단됨

**의도한 규칙**: 서로 다른 그래프의 기존 노드끼리(단, 양쪽 그래프의 **루트 노드는 제외**) 핸들 간 드래그로 연결할 수 있다. 이때 양쪽 모두 부모 반대 방향 핸들, 즉 각자의 source 핸들을 사용한다.

**실제 동작**: 루트가 아닌 노드는 정의상 부모를 갖고 있으므로, 어느 쪽이 자식이 되든 단일 부모 검사(#92)가 연결을 차단한다. 결과적으로:

- 루트 제외 노드끼리의 그래프 간 연결 (의도한 케이스) → **전부 차단**
- 부모 없는 일반 루트를 자식으로 편입하는 연결 (규칙이 제외한 케이스) → 허용
- 즉 의도와 정확히 반대 케이스만 살아남은 상태

**원인**: 그래프 간 엣지와 부모-자식 엣지가 데이터 구조상 구분되지 않아(§0-6), 그래프 간 연결도 누군가의 incoming 엣지 = "두 번째 부모"가 되기 때문.

**차단은 한 겹이 아니라 세 겹이다** — 단일 부모 검사만 풀어도 아래 두 층이 더 막는다:

1. **단일 부모 검사 (#92)**: 위에서 서술.
2. **엣지 레코드의 의미**: 연결 확정 시 핸들 필드가 "부모의 바깥 핸들 → 자식의 부모 방향 핸들" 형태로 재라벨링된다(§0-9). 양쪽 다 부모가 있는 링크는 어느 쪽도 상대의 자식이 아닌데, 저장하는 순간 한쪽이 강제로 '자식'으로 기록된다.
3. **핸들 렌더링·표현 재계산**: 부모 있는 노드는 자유 방향에 target 핸들이 없으므로(§4), 2번처럼 재라벨링된 엣지는 존재하지 않는 핸들을 가리키게 되어 React Flow가 콘솔 에러 #008(`Couldn't create edge for source/target handle id ...`)을 내고 엣지 렌더링에 실패한다. 설령 앵커가 된다 해도 `buildEdgePresentation`이 엣지 양끝 핸들을 target 노드의 handleSide — 그 노드의 **자기 부모** 기준 값 — 로 재계산하므로, 이 링크와 무관한 방향이 적용된다.

따라서 그래프 간 엣지를 별도 타입(링크)으로 승격하려면 `getParentId`가 링크를 부모로 세지 않게 하는 것만으로는 부족하고, **양끝을 각자의 source 핸들로 저장하는 별도 핸들 의미 + 부모-자식 전제를 우회하는 렌더 경로 + 엣지 메타데이터의 백엔드 영속화**가 모두 필요하다 (`getSameColorDescendantIds` CONTEXT의 Alternatives ② — 보류 중).

**→ 해결 설계 확정 — 구현 대기 ([AiDeep-web#133](https://github.com/Won-Life/AiDeep-web/issues/133))**: 노드에 소속 그래프 uuid(`graphId`)를 영속화하고([Aideep_backend#55](https://github.com/Won-Life/Aideep_backend/issues/55)) 링크를 "양끝 graphId 불일치"로 유도한다(엣지 스키마 무변경). 판정 순서: 같은 graphId 차단 → main↔main 차단 → 무-project 그래프는 depth 0 루트부터 통째 편입(사각형 하이라이트 + 부착 방향 재정렬, [Aideep_backend#56](https://github.com/Won-Life/Aideep_backend/issues/56) 필요) → project 그래프끼리는 source-source 링크. 위 3번째 겹의 "우회 렌더 경로 필요" 서술은 과대평가로 확인됨 — xyflow loose 모드는 `targetHandle` id를 target 노드의 source 핸들에서도 찾으므로(`getEdgePosition` fallback), 실존하는 `source-*` id를 저장하면 앵커되고, `buildEdgePresentation`의 링크 분기(각 끝을 각자 노드의 현재 handleSide로 재계산)로 충분하다.

### 10-2. ⚠️ 색상 = 그래프 경계 방식의 알려진 구멍

- 두 그래프가 우연히 같은 색이면 경계를 판별하지 못한다 (이동·전파·삭제가 상대 그래프까지 번질 수 있음)
- 색 미저장 legacy 메인 노드는 첫 커스텀 색 자식으로 색을 추정하므로, 그래프 간 엣지의 자식이 먼저 잡히면 상대 그래프 색으로 오판 가능 (Aideep_backend#52 대기)
- → graphId 도입(AiDeep-web#133)으로 색을 경계 판정에서 전면 제거하는 설계 확정 — 구현 대기

### 10-3. ⚠️ 대칭 이동의 핸들 방향 변경이 서버에 저장되지 않음 — 새로고침 시 **확정** 발생 (로컬 렌더는 해결)

엣지 API는 생성/삭제만 있고 수정(PATCH)이 없다 (PATCH 신설 요청: [Aideep_backend#56](https://github.com/Won-Life/Aideep_backend/issues/56), OPEN). 두 대칭 경로(§5-2) 모두 노드 위치는 d3 좌표에 반영돼 드래그 종료 시 **새 위치는 서버에 저장되는데**, 함께 바뀐 handleSide·엣지 핸들은 로컬에만 남는다.

이 결함은 두 층위로 나뉜다:

- **로컬 렌더(세션 중) — 해결**: 렌더 엣지는 `buildEdgePresentation`이 매 렌더 **타깃 노드의 `handleSide`**에서 sourceHandle/targetHandle/hub를 재계산한다(§4). 따라서 대칭 시점에 자손 노드의 `handleSide`만 새 방향으로 갱신하면 세션 중 교차 렌더링은 사라진다. 드래그 중 대칭은 원래부터 이 갱신을 했고(§5-2), 드래그 종료 대칭도 이제 동일하게 갱신한다(setEdges 불필요 — 렌더가 handleSide에서 파생하므로). raw 엣지의 `sourceHandle`은 낡은 채 남지만 렌더에 안 쓰이고 저장도 안 돼 무해.
- **서버 저장(새로고침 후) — 미해결(#56 대기)**: 마운트 초기화(§4)가 DB의 `sourceHandle`을 신뢰하므로, 대칭만 하고 새로고침하면 **확정적으로** 노드는 새 방향 위치에 있는데 엣지는 옛 방향 핸들에서 나가는 교차 렌더링이 된다. 유일한 우회책(삭제+재생성)은 중간 실패 시 엣지 소실·edgeId 변경·중간 빈 상태 노출이라 #56이 명시적으로 기각했다. `PATCH /edge/:edgeId` 머지 후 두 대칭 경로에 저장 호출을 추가하면 완결.

(드래그 종료 시점 대칭 이동은 위치조차 저장되지 않던 별개 문제였고 §10-7에서 해결됨.)

### 10-4. 노드 드래그 편입 경로의 순환 생성 — 해결 (조상·형제 재부모화는 여전히 허용)

핸들 드래그와 달리 노드 드래그 편입(§3-5)·리소스 드롭은 축약된 검사(`isInvalidConnection`)만 거친다. 과거 이 검사가 직접 부모-자식만 차단해 두 가지 문제가 있었다:

1. **순환 생성** — 자기 **자손**에 스냅하면 순환(자손이 조상의 부모가 됨)이 생긴다. 일반 드래그에서는 서브트리가 함께 움직여 상대 거리가 유지되므로 만들기 어렵지만, **opt/alt 단독 이동(§5-1)은 자식이 따라오지 않으므로 부모를 자기 손자 옆(감지 범위 50px 이내)까지 그대로 가져갈 수 있어** 손자→부모 엣지가 생성됐다.
2. **무한 루프** — 순환이 생기면 조상 탐색(`getAncestorIds`)이 방문 체크 없이 부모를 따라가 다음 렌더에서 무한 루프 → **탭 정지(화면 멈춤)**.

**해결 (두 겹, 클라 완결)**:

- [x] **생성 차단**: `isInvalidConnection`에 순환 가드 추가 — 부모가 될 노드(source)가 이미 자식이 될 노드(target)의 자손이면(`getDescendantIds(target).has(source)`) 차단. 모든 연결 경로가 이 공유 함수를 거치므로 편입·핸들 드래그·hover 감지가 한 번에 막힌다.
- [x] **폭주 방지**: `getAncestorIds`에 방문 체크(`!ancestors.has(current)`) 추가 — 레거시·경합으로 순환 엣지가 이미 남아 있어도 조상 탐색이 유한하게 끝나 탭 정지가 재발하지 않는다.

남은 것(미해결): 자손이 아닌 **조상·형제**로의 스냅(같은 그래프 내 재부모화)은 여전히 허용된다. 순환도 단일 부모 위반도 아니라 구조상 유효하나, 의도된 동작인지 규칙으로 확정된 바 없다 → 같은 그래프 검사 도입 시(graphId, AiDeep-web#133) 정책 결정.

### 10-5. 메인 노드 없는 그래프에서 자손 → 루트 핸들 연결 순환 — 해결

"같은 그래프" 검사는 두 노드가 **같은 메인 노드**를 공유하는지로 판별하므로, 메인 노드가 없는 그래프(일반 노드 루트)에서는 동작하지 않는다. 이때 자손 노드에서 부모 없는 루트로 핸들 드래그하면 루트가 자손의 자식으로 편입되어 순환이 생겼다.

- [x] §10-4의 `isInvalidConnection` 순환 가드가 이 경로도 막는다 — 자손 D에서 루트 R로 드래그하면 source=D(부모)·target=R(자식)이고 D는 R의 자손이므로 `getDescendantIds(R).has(D)`가 true라 차단된다. 메인 노드 유무와 무관하게 동작.
- [x] `getAncestorIds` 방문 체크로 화면 멈춤도 방지.

(graphId 도입 시의 "같은 graphId 차단"(AiDeep-web#133)은 조상·형제 재부모화까지 포함해 더 넓게 막는 별개 설계 — 순환 차단 자체는 위로 완결.)

### 10-6. 형제·조상 차단이 전용 규칙이 아닌 부수 효과로 성립

"형제·부모·조상 노드와 연결 불가" 규칙은 전용 검사가 없다. 직접 부모-자식만 명시 차단이고, 형제·조상은 같은 그래프 검사(메인 그래프 한정)와 단일 부모 검사의 부수 효과로 차단된다. (사용되지 않던 `areSiblings` 데드 코드는 제거됨.) 조상·형제 재부모화가 여전히 허용되는 구멍은 §10-4 참고.

### 10-7. 드래그 편입(스냅)의 위치 보정이 서버 저장에서 누락됨 — 해결

전제: 드래그 중 위치의 단일 진실은 d3 시뮬레이션 좌표이고, 드래그 종료 시 자손들의 위치 저장(`moveNode`)도 d3 좌표를 읽는다(§5-3). 편입 스냅(§3-5)이 일어나면 두 가지 위치 보정이 발생한다:

1. 자식(+서브트리)을 새 부모 옆 자동 배치 위치로 옮기는 스냅 이동
2. 서브트리가 연결 방향 반대에 있을 때의 종료 시점 대칭 이동(`mirrorSubtree`)

**해결 ①(좌표 소스)**: 두 보정을 계산할 때 `d3NodesRef.current`의 해당 자손 좌표도 함께 갱신한다(스냅은 같은 delta 가산, 대칭은 중심점 `2*axis - center`). 저장 경로(`moveNode`)는 무수정이고, d3 좌표가 곧 화면과 일치하므로 자손도 보정된 위치로 저장된다. 드래그 노드 **본인**은 원래부터 `finalPosition`으로 별도 저장돼 문제없었다.

**해결 ②(저장 대상 집합)**: **메인 노드를 드래그해 다른 노드를 편입시킨 경우**, 이동하는 쪽은 편입되는 상대 노드(+그 서브트리)인데, 종료 시 저장 대상 집합(`getSameGraphDescendantIds(draggedNode)`)은 "메인의 같은 색 자손"이라 상대를 포함 못 한다(저장 시점에 상대 색은 아직 옛 색, 새 엣지도 REST 응답 전이라 로컬 엣지에 없음). 이 상대 서브트리 id 집합(`incorporatedIds`)을 스냅 시점에 따로 담아두고(=①에서 d3 좌표를 고쳐둔 그 집합), 종료 시 별도 `moveNode` 루프로 저장한다. 이 노드들은 드래그 대상이 아니라 `fx/fy`가 걸린 적 없어 해제도 불필요.

이로써 일반 노드 편입·메인 노드 편입 두 케이스 모두 자손 위치가 서버에 보정된 값으로 저장된다. (대칭 시 자손 handleSide·엣지 핸들 미갱신 문제는 §10-3 별개.)

### 10-8. ⚠️ 다중 선택 드래그는 그래프(색) 경계를 무시함

단일 노드 드래그는 고정·프레임 이동·종료 저장 세 지점 모두 "같은 색 자손"만 대상으로 한다(§5-1). 그런데 다중 선택 드래그에서 함께 선택된 **다른** 노드들의 서브트리는 색 경계 없는 **전체 자손 순회**(`getDescendantIds`)를 쓴다. 결과:

- 그래프 간 엣지 너머의 다른 그래프 노드가 통째로 딸려 이동하고, 그 위치가 서버에 저장까지 된다 — §5-1의 "다른 그래프는 따라오지 않음" 규칙과 정면 모순
- 같은 드래그 안에서도 직접 잡은 노드(색 경계 적용)와 나머지 선택 노드(전체 순회)가 서로 다른 규칙을 적용받는다

### 10-9. ⚠️ 드래그 중 협업자의 노드 이동이 내 화면에서 되돌아감

드래그 중 d3 tick은 **드래그 시작 시점에 떠 놓은 스냅샷** 기준으로 캔버스의 모든 노드 위치를 매 프레임 화면에 덮어쓴다(§5-3). 내가 드래그하는 동안 협업자가 옮긴 노드는 WS로 반영되자마자 옛 위치로 되돌아가고, 내 드래그가 끝난 뒤에도 그 노드를 다시 그려줄 계기가 없어 다음 WS 이벤트나 새로고침 전까지 어긋난 채 남는다.
