# 그래프 도메인 규칙 (Living Document)

그래프 캔버스의 기능 명세이자 구현 체크리스트. **실제 코드 동작 + 서버 계약 기준으로 서술한다.**
**구현·수정 작업에서 그래프 동작이 바뀌면 이 문서의 해당 항목을 같은 브랜치에서 함께 갱신한다.**

- `[x]` 구현 완료 / `[ ]` 미구현
- 코드 진입점: `src/features/graph/components/GraphCanvas.tsx`
- AI 작업 규칙(패턴·불변식)은 `src/features/graph/CLAUDE.md` 참고 — 이 문서는 "무엇을 해야 하는가 + 실제로 어떻게 동작하는가", CLAUDE.md는 "구현 시 지켜야 할 패턴"
- 핸들 방향(`handleSide`) 체계의 설계 배경은 [AiDeep-web#58](https://github.com/Won-Life/AiDeep-web/pull/58) 참고
- §11은 코드 동작 서술이 아니라 **설계 결정과 미해결 과제**다 — 동작을 바꾸는 결정이 내려지면 §11과 본문을 함께 갱신한다.

## 0. 용어와 기본 구조 (전제)

이 문서 전체가 아래 전제 위에서 서술된다.

1. **그래프** = 엣지로 연결된 노드들의 집합. 한 워크스페이스 캔버스에 여러 그래프가 공존한다.
2. **엣지의 방향이 곧 부모-자식 관계다.** `edge.source` = 부모, `edge.target` = 자식. 부모 판별(`getParentId`)은 "나를 target으로 갖는 엣지의 source"로만 판단하며, 색상·위치는 부모 판별에 쓰지 않는다.
3. **트리 전제**: 모든 노드는 부모(incoming 엣지)를 최대 1개만 가진다 (#92). 그래프의 **루트**는 부모 없는 노드(`depth === 0`)이며, 메인(PROJECT) 노드이거나 부모 없는 일반 노드다.
4. **메인 노드**(`data.isMain`, `node_type === 'PROJECT'`): 프로젝트 중심 노드. 연결 시 항상 부모(source)가 되고, 화면에는 흰색으로 표시되지만 내부적으로 그래프 색을 `data.color`에 보유한다.
5. **그래프 소속의 식별자는 색상이다.** 같은 색 = 같은 그래프. 서브트리 순회 자체는 엣지(source→target) 기반 BFS(`getDescendantIds`)이고, 색상은 "어디까지가 내 그래프인가"라는 **경계 판단**에만 쓰인다(`getSameColorDescendantIds`). 색이 경계로 쓰이는 이유와 남은 역할은 §11-설계 참고.
6. **depth**: 각 노드는 `data.depth`(트리 루트로부터의 거리)를 가진다. `depth === 0`이면 루트(부모 없음). 서버 sync 값이 초기값이고 신규 노드는 0. 루트 판별·대칭 축·같은 그래프 판정 기준점이 모두 depth로 결정된다(§4·§5-2, `src/features/graph/CLAUDE.md`).
7. **handleSide**: 자식 노드가 부모의 왼쪽/오른쪽 어느 방향에 붙는지(`'left' | 'right'`). `node.data.handleSide`에 저장되며 엣지의 `sourceHandle`/`targetHandle`과 짝을 이룬다. side가 `right`이면 엣지는 `source-right` → `target-left`로 연결된다(`resolveHandleId`). handleSide는 클라이언트 로컬 상태이며 서버는 저장하지 않는다 — 마운트 시 엣지 `sourceHandle`에서 재유도한다(§4).
8. **동기화**: 본인 변경은 REST 응답 후 로컬 state 반영(낙관적 삽입 없음 — 단 연결 시 색·위치 선반영 예외는 §3-3), 협업자 변경은 WS 이벤트로만 반영. 서버는 WS 이벤트를 **발신자 제외**로 broadcast한다(per-user 룸 `.except()`, Aideep_backend#47).
9. **핸들 제스처와 엣지 레코드는 다른 층위다.** React Flow는 loose 모드(`ConnectionMode.Loose`)이고 모든 target 핸들이 연결 시작 불가(`isConnectableStart={false}`)이므로, 연결 드래그는 **source 핸들에서만 시작**할 수 있고 상대의 source·target 어느 핸들에나 드롭할 수 있다 — 즉 source 핸들끼리 잇는 제스처도 허용된다. 반면 저장되는 엣지 레코드의 `sourceHandle`/`targetHandle` 필드는 "부모의 바깥 방향 핸들 → 자식의 부모 방향 핸들"이라는 의미로 고정되어 있어서, 연결 확정 시(`onConnect`) 부모/자식을 정한 뒤 실제 드롭 지점과 무관하게 필드를 `source-*` / `target-*` 쌍으로 **다시 써서 저장**한다(정규화). 이 재라벨링이 시각적으로 문제없는 이유는, 현재 허용되는 연결에서 자식이 되는 쪽이 항상 부모 없는 노드이고 부모 없는 노드는 source 핸들과 같은 자리에 숨김 target 핸들을 함께 렌더링하기 때문이다(§4). 양쪽 다 부모가 있는 노드끼리의 연결은 §3-2에서 차단되므로 이 정규화가 깨지는 케이스는 발생하지 않는다.

## 3. 연결 생성 (4경로)

연결이 만들어지는 경로는 네 가지이며, **경로마다 부모 결정·검사 규칙이 다르다.**

| # | 경로 | 트리거 | 상세 |
|---|------|--------|------|
| 1 | 핸들 드래그 — 기존 노드 연결 | 핸들에서 엣지를 뽑아 다른 노드에 드롭 | §3-3 |
| 2 | 핸들 드래그 — 새 노드 생성 | 핸들에서 엣지를 뽑아 빈 공간에 드롭 | §3-4 |
| 3 | 노드 드래그 편입 | 노드를 다른 노드 근처(50px)에 드래그해 놓음 | §3-5 |
| 4 | 리소스 드롭 | 사이드바 리소스를 노드 근처(50px)에 드롭 | §3-6 |

§3-1·§3-2는 연결 확정 전에 거치는 **공통 점검 규칙**(방향 결정·연결 제한 — 단 경로별 적용 범위가 다름), §3-3~§3-6은 **경로별 동작**이다.

### 공통 점검 규칙

#### 3-1. 부모/자식 방향 결정 — 핸들 드래그 경로 (`resolveConnectionDirection`)

핸들 드래그 A→B는 기본적으로 A=부모(source), B=자식(target)이다. 아래 경우에만 방향을 뒤집는다(swap):

1. **메인 노드는 항상 부모** — 메인 노드가 드래그의 도착점(B)이어도 메인이 source가 된다
2. **단독 노드(엣지 0개)가 그래프에 연결되면 그래프 쪽이 부모** — 단독 노드가 드래그를 시작했어도 그래프에 편입되는 자식이 된다

`onConnect`(연결 확정)와 `isValidConnection`(드래그 중 유효성 표시)이 같은 헬퍼를 공유한다 — 검사와 실제 연결의 방향 판단이 어긋나지 않게 하기 위함.

#### 3-2. 연결 제한 (경로별로 적용 범위가 다름)

**핸들 드래그(`isValidConnection`)에서 차단되는 것:**

- [x] 자기 자신과 연결
- [x] 메인 노드 ↔ 메인 노드
- [x] 직접 부모-자식 재연결 (이미 연결된 쌍)
- [x] **같은 그래프(같은 depth 0 루트 공유)에 속한 노드끼리** — 루트 ↔ 서브 재연결 방지, 조상·형제도 이 검사로 차단 (`getRootNodeForSubtree` 비교, #146)
- [x] **서로 다른 그래프끼리** — 둘 다 엣지를 가진 노드인데 `data.color`가 서로 다르면 차단 (§11-설계: 크로스 그래프 연결 차단). 색 미확정(색 미저장 legacy 메인)은 오판 방지를 위해 통과시킨다
- [x] **단일 부모 불변식 (#92)**: swap 이후의 실제 자식이 이미 부모를 가지면 차단
- [x] **부모가 있는 노드의 부모 방향(`target-*`) 핸들로 들어오는 연결** — 연결은 부모 반대 방향으로만. swap으로 그 노드가 부모가 되는 케이스도 드롭 지점이 부모 방향이면 차단 (부모 없는 노드의 target 핸들 드롭은 허용)

`onConnect`는 드래그 중 `isValidConnection`이 이미 걸러준다는 전제 위에서, 프로그래매틱 연결 대비로 **단일 부모·target 핸들 두 검사만** 이중 방어한다 (색·같은 그래프 재검사는 하지 않음, §3-3).

**노드 드래그 편입·리소스 드롭(`isInvalidConnection`만 사용)에서 차단되는 것:**

- [x] 자기 자신 / 메인 ↔ 메인 / 직접 부모-자식
- [x] **순환 차단**: 부모가 될 노드(source)가 이미 자식이 될 노드(target)의 자손이면 차단 — `getDescendantIds(target).has(source)`로 판정. 모든 연결 경로가 이 함수를 거치므로 핸들 드래그·편입·hover 감지가 한 곳에서 막힌다
- 같은 그래프 검사·단일 부모 검사는 **하지 않는다**. 노드 드래그 편입은 기존 부모 엣지를 끊고 재연결(재부모화)하므로 단일 부모는 결과적으로 유지되며, 조상·형제로의 재부모화는 의도적으로 허용된다 (§11-설계: 조상·형제 재부모화)

참고: 형제·조상 연결 차단은 전용 검사가 아니라 "같은 그래프 검사 + 단일 부모 검사"의 부수 효과다 (§11-설계).

### 경로별 동작

#### 3-3. 핸들 드래그 — 기존 노드끼리 연결 (`onConnect`)

1. 방향 결정(§3-1) 후 단일 부모·target 핸들 검사(§3-2) 통과 시 진행
2. 서로 다른 그래프끼리는 `isValidConnection`에서 차단되므로 여기 도달하는 연결은 **단독 노드·같은 색 트리뿐** — **항상** 자식(+그 서브트리)을 부모 기준 자동 배치 위치로 이동시키고, 부모 그래프 색을 자식 서브트리에 전파한다(편입)
3. 자식의 `handleSide` 저장: swap 반영 후 source 쪽 핸들 이름에서 left/right 추출 → 핸들 이름에 방향이 없으면 위치 기반 fallback
4. **서버 반영 순서**: 색·위치는 `createEdge` REST **요청 전에** 로컬 선반영(엣지 생성 실패 시 롤백 없음), 엣지 자체는 REST 성공 후에만 로컬 삽입, 색상 저장은 엣지 생성 성공 후 대상 노드별 `updateNodeContent` PATCH, **위치 저장은 엣지 생성 성공 후 `saveDragPositions`** — 자식 root만 `moveNode` PATCH하고 서버 delta 전파와 어긋나는 자손(대칭이동분)만 보정 (§5의 드래그 저장과 동일 패턴)

#### 3-4. 핸들 드래그 — 빈 공간 드롭으로 새 노드 생성 (`onConnectEnd`)

노드 생성 자체(REST 순서·겹침 시 미생성)는 §2의 "핸들 드래그 → 빈 공간 드롭" 행과 같은 경로 — 여기서는 연결 관점만 서술한다.

- [x] **부모는 항상 드래그 시작 노드** — 새 노드는 생성 직후라 엣지가 없으므로 방향 swap(§3-1)·연결 제한(§3-2)이 개입할 상황이 없다
- [x] 새 노드는 시작 노드의 그래프 색을 **생성 시점에 부여**받는다 (연결 후 색 전파가 아님)
- [x] side 결정: 그래프 소속(부모 있는 노드)이면 루트 반대(바깥) 방향 강제(`getForcedOutboundSideForSubNode`) → 시작 핸들 이름의 left/right → 부모(없으면 depth 0 루트) 기준 위치 fallback (§4 표와 동일, #146)
- [x] 서버 반영 순서: `createMdNode` 성공 → 노드 로컬 삽입 → `createEdge` 성공 후 엣지 로컬 삽입. 엣지 생성이 실패하면 **그래프 색만 입은 독립 노드가 남는다** (콘솔 로그만, 롤백 없음)

#### 3-5. 노드 드래그 편입 (`onNodeDragStop`, hover-snap)

- [x] 노드 A를 드래그해 노드 B 근처(50px)에 놓으면 연결 생성 — hover 시 B가 커지는 효과
- [x] **부모 결정**: 드래그한 노드가 메인이면 드래그한 쪽이 부모, 그 외에는 **hover된 노드(B)가 항상 부모**
- [x] **재부모화**: 자식(A)에 기존 부모가 있으면 기존 부모 엣지를 로컬·서버 모두 삭제하고 B → A로 재연결
- [x] **side 결정**: 부모가 루트(depth 0)면 자식의 상대 위치 기반, 부모가 depth>0이면 **부모의 handleSide 계승** (트리가 같은 방향으로 계속 뻗어나가도록)
- [x] 자식(+같은 그래프 서브트리)을 부모 기준 자동 배치 위치로 스냅
- [x] 스냅 후 서브트리 평균 중심이 연결 방향과 반대에 있으면 서브트리를 대칭 이동(§5-2)
- [x] 부모 그래프 색을 자식 서브트리에 전파 (로컬 페인트 + 노드별 PATCH)
- [x] 다중 선택 드래그 중에는 hover-snap 비활성화

#### 3-6. 리소스 드롭 연결 (`onDrop`)

- [x] hover된 노드가 있고 유효하면: 새 노드를 hover 노드의 자식으로 생성 + 연결
- [x] side 결정: hover 노드에 `handleSide`가 있으면 계승, 없으면 드롭 위치 기반 (§3-5는 depth로, §3-6은 handleSide 유무로 분기 — 루트/메인은 handleSide가 없어 실질 동일)

## 4. handleSide (핸들 방향) 규칙 — AiDeep-web#58

핸들 방향은 **위치가 아니라 연결 관계(topology)로 결정**된다. 위치는 드래그 중 계속 바뀌므로 위치 기반 재계산은 엣지 방향이 흔들리는 근본 원인이었다. topology가 바뀌는 시점에만 명시적으로 갱신한다.

| 시점 | handleSide 결정 기준 |
|------|---------------------|
| 마운트 (`initializeHandleSides`) | incoming 엣지의 `sourceHandle`에서 추출 (서버 데이터 기반) |
| 핸들 드래그 연결 (`onConnect`) | swap 반영 후 source 핸들 방향 → 위치 fallback |
| 노드 드래그 편입 (`onNodeDragStop`) | 부모가 루트 → 위치 / depth>0 → 부모 계승 |
| 리소스 드롭 (`onDrop`) | 부모가 루트 → 드롭 위치 / depth>0 → 부모 계승 |
| 핸들 드래그 새 노드 생성 (`onConnectEnd`) | 그래프 소속이면 루트 반대(바깥) 방향 강제 → 핸들 이름 → 위치 |
| 대칭 이동 (§5-2) | 새 side로 일괄 갱신 + 드래그 종료 시 엣지 핸들 서버 저장 |
| 단순 위치 이동 | **변경 없음** (갱신하면 DB `sourceHandle`과 불일치 → 새로고침 시 엣지 방향이 튐) |

- [x] 엣지 렌더링(`buildEdgePresentation`)은 `node.data.handleSide`(storedSide)를 최우선 참조 — 드래그 중 position이 바뀌어도 핸들이 흔들리지 않음
- [x] 메인 노드 자신은 handleSide를 갖지 않음 (양방향으로 자식을 가질 수 있으므로)
- [x] **핸들 렌더링 구조** (`src/features/nodes/TextUpdateNode.tsx`) — §0-9 정규화를 이해하는 전제:
    - **부모 없는 노드 = 핸들 4개**: 양쪽에 source 핸들(hover 시에만 표시, 드래그 시작 가능) + 같은 자리에 겹쳐진 숨김 target 핸들(드롭 앵커 전용). 그래서 어느 방향으로든 연결 가능하고, source 핸들에 드롭된 연결을 target 핸들 라벨로 저장해도 같은 위치에 앵커된다
    - **부모 있는 노드 = 핸들 2개뿐**: 부모 방향에 숨김 target 핸들, 부모 반대 방향에 source 핸들. **부모 반대(자유) 방향에는 target 핸들이 없다** — 부모 있는 노드를 target으로 기록한 엣지는 그 노드의 부모 방향에만 앵커할 수 있다
    - 모든 target 핸들은 연결 시작 불가 → 연결 드래그는 항상 source 핸들에서 시작된다

## 5. 노드 이동

### 5-1. 기본 드래그

- [x] 메인 노드 드래그 → 같은 그래프(같은 색) 전체가 함께 이동
- [x] 일반 노드 드래그 → 해당 노드 + 같은 그래프 서브트리가 함께 이동 (다른 그래프 노드는 따라오지 않음 — 색 경계)
- [x] 형제 노드가 있어도 선택한 노드(+서브트리)만 이동
- [x] opt/alt + 드래그 → 서브트리를 떼어놓고 드래그한 노드만 단독 이동
- [x] 다중 선택 드래그(shift+클릭·박스 선택으로 2개 이상 선택 후 이동): 선택된 모든 노드 + 각자의 서브트리가 함께 이동 — 색 경계 없는 전체 순회(`getDescendantIds`), 다른 그래프도 함께 딸려감 (§11-설계: 다중 선택 드래그)
- [x] 드래그 중 엣지도 실시간으로 따라 움직임 (허브 이후 평행선이 늘어나는 형태)

### 5-2. 대칭 이동 (mirror)

대칭 이동은 **드래그 중**과 **드래그 종료 시** 두 경로가 있고, 트리거·구현이 다르다 (같은 드래그에서 이중 적용은 없음 — 두 경로는 발동 조건이 배타적으로 순차 실행됨).

**드래그 중 대칭** — 루트(depth 0) 노드의 직계 자식을 드래그해 루트의 좌우 축을 넘긴 순간 (#146):

- [x] 드래그 노드는 마우스를 그대로 따라가고, 서브트리만 드래그 노드 기준 거리를 유지한 채 반대편으로 대칭 이동 — **d3 시뮬레이션 좌표를 직접 변경**하므로 드래그 종료 시 새 위치가 서버에 저장됨
- [x] 축 판정 기준은 depth 0 루트(`getRootNodeForSubtree`) — 조상 체인에 depth 0이 없으면 체인 끝 노드를 루트로 간주. 축 X 좌표는 `rootNode.position.x + (rootNode.width ?? NODE_WIDTH) / 2`
- [x] 드래그 노드 + 서브트리의 handleSide와 관련 엣지의 핸들·허브 좌표를 새 방향으로 일괄 갱신. 드래그 종료 시 시작 시점 핸들 스냅샷(`dragStartEdgeHandlesRef`)과의 diff로 바뀐 엣지만 `PATCH /workspace/:id/edge/:edgeId`로 서버 저장 — 반전만 하고 빈 공간에 놓아도 새로고침 후 일관

**드래그 종료 시 대칭** — 편입 스냅(§3-5) 후 서브트리 평균 중심이 연결 방향 반대에 있으면:

- [x] 서브트리를 새 부모 기준 축으로 대칭 이동 (`mirrorSubtree`, 중심점 대칭 `2*axis - center`)
- [x] 뒤집힌 위치를 d3 좌표(`d3NodesRef`)에도 동기화 → 자손 저장이 보정된 위치로 나감
- [x] 대칭된 자손의 `handleSide`를 새 방향(부모 기준 side)으로 갱신 → 렌더 엣지는 `buildEdgePresentation`이 타깃 노드 handleSide에서 핸들·hub를 재계산하므로 세션 중 교차 렌더링 없음
- [x] 뒤집힌 서브트리 내부 엣지 핸들은 `persistSubtreeEdgeHandles`가 `PATCH /workspace/:id/edge/:edgeId`로 서버 저장 (이미 새 방향인 엣지는 건너뜀) — 새로고침 후에도 일관. 자손 handleSide는 로컬 갱신뿐이며 마운트 시 저장된 엣지 핸들에서 재유도(§4)

**공통**:

- [x] **대칭 이동 시 그래프 간 엣지 절단**: 색이 다른(다른 그래프) 직계 자식은 대칭 이동을 따라오지 않아 연결 방향 규칙이 꼬이므로, 해당 엣지를 로컬·서버 모두 삭제 (`findCrossColorChildEdges`, 드래그 중에도 즉시 DELETE)

### 5-3. 화면 상 이동 vs 서버 저장 시점

드래그 중 화면의 움직임과 서버 저장은 **완전히 분리**되어 있다:

1. **드래그 중** — 서버 DB에는 아무것도 저장하지 않는다.
   - **위치의 단일 진실은 d3 시뮬레이션 좌표(`d3NodesRef`)**: 드래그 노드는 마우스 위치가 d3 고정 좌표(fx/fy)로 복사되고, 서브트리는 프레임 delta가 fx/fy에 누적되며, d3 tick이 매 프레임 **캔버스의 모든 노드**를 d3 라이브 좌표로 화면(React state)에 일괄 반영 (충돌 force로 밀려나는 주변 노드 포함)
   - tick이 d3 라이브 좌표로 전체를 덮어쓰므로, 드래그 중 협업자가 WS로 옮긴 노드는 d3 좌표에 반영되지 않아 내 화면에서 옛 위치로 되돌아감 (§11-미해결: 드래그 중 협업자 이동)
   - 협업자 화면 표시용으로 **드래그 노드의 위치만** WS `emitLivePosition`으로 브로드캐스트 (50ms throttle) — 실시간 표시용이며 위치 영속화가 아님. 서브트리 위치는 브로드캐스트되지 않아 협업자에게는 드롭 순간 한 번에 점프해 보임
   - 예외: 대칭 이동으로 절단되는 그래프 간 엣지는 드래그 **중에도** `deleteEdge` REST 즉시 호출
2. **드래그 종료 (`onNodeDragStop`)** — 이 시점에 비로소 REST로 저장한다 (PR #144).
   - **전제**: 서버 `PATCH /workspace/:id/node/:id/move`는 대상 노드를 절대 좌표로 저장하면서 **DB 기준 delta를 모든 자손에게도 전파**한다(색 경계 무시). 부모·자손을 각각 병렬 PATCH하면 자손이 두 경로로 쓰여 이중 이동되므로, root만 저장하고 자손은 보정한다.
   - **순차 저장 + 보정** (`saveDragPositions`): 드래그한 노드(root)만 PATCH → 응답 후, 드래그 시작 스냅샷(`dragStartPositionsRef`)으로 서버 전파 결과를 시뮬레이션 → 로컬 최종 위치와 어긋나는 자손만 조상→자손 순서로 순차 보정 PATCH (보정 자체가 일으키는 자손 전파도 시뮬레이션에 누적 반영, 0.5px 허용오차).
   - 일반 드래그(서브트리 평행이동)는 요청 1건으로 끝. 대칭 이동·opt/alt 단독 이동·그래프 간 엣지 너머 자손처럼 서버 전파가 로컬과 어긋나는 노드만 보정이 나간다.
   - 저장 좌표는 스냅·대칭 보정까지 커밋된 React state(`nodesRef`)에서 종료 후 `setTimeout(0)`으로 읽는다.
   - 메인 노드 드래그 편입 시 상대 서브트리의 **root**(`incorporatedIds`)를, 다중 선택 드래그 시 선택된 각 노드를 같은 순차 저장 목록(`rootsToSave`)에 추가 — 모두 root만 태우고 자손은 보정으로 처리 (다중 선택 이동이 색 경계를 무시하는 것은 의도된 동작 — §11-설계)
   - 함께 바뀐 엣지 핸들은 시작 스냅샷 diff로 서버 저장 (§5-2)
   - 시뮬레이션에 **밀려나기만 한** 주변 노드의 위치는 저장하지 않는다 → 새로고침 시 밀려난 노드는 원위치로 복귀 (§11-미해결)

## 6. 색상 규칙

- [x] 그래프 소속 = 색상 (§0-5). 새 그래프의 색은 랜덤 페어(`getRandomColorPair`)
- [x] 연결 생성 시 부모 그래프 색이 자식 서브트리에 전파 — 로컬 페인트(`updateSubtreeColors`)와 서버 저장이 **같은 집합**(`getRecolorTargetIds`: 루트 + 같은 색 자손, 메인 제외)을 사용
- [x] 색상 저장은 대상 노드별 `updateNodeContent` PATCH. 서버의 `propagateToChildren` 전파는 그래프 색 경계를 모르고 그래프 간 엣지 너머까지 덮어쓰므로(Aideep_backend#51) 사용하지 않음. PATCH 실패해도 로컬 색상은 유지(롤백 없음)
- [x] 엣지 삭제로 그래프에서 분리되면: 남은 부모가 없으면 자식 서브트리를 기본 회색으로, 다른 부모가 남아 있으면 그 그래프 색으로 재페인트 — target 쪽만 변경, source 쪽 불변
- [x] 메인 노드도 그래프 색을 `data.color`에 저장 (화면 표시만 흰색). 색 없는 legacy 메인 노드는 색이 확정되는 시점(연결 생성 등)에 로컬+서버로 색을 채움(`backfillMainColor`) — 그 전까지는 첫 커스텀 색 자식의 색으로 추정하는 폴백 동작 (§11-미해결: legacy 데이터 정리)
- [ ] 노드 depth 별 색상 밝기 처리

## 7. 삭제·보관

- [x] 노드 삭제 = 보관 처리. Backspace·컨텍스트 메뉴 모두 확인 모달을 거침 (대상 개수 표시)
- [x] 같은 그래프(같은 색) 서브트리가 함께 보관됨 — 삭제 캐스케이드도 색 경계에서 멈추고, 그래프 간 엣지로 이어진 다른 그래프의 노드는 제외. 두 그래프를 잇던 엣지는 서버가 노드 삭제 시 함께 지우므로(연결 엣지 hard-delete) 상대 그래프는 자기 루트로 독립
- [x] 서버 `deleteNode` 병렬 호출이 **모두 성공한 후에만** 로컬 state에서 제거 — 실패 시 화면 유지
- [x] 일부 노드 삭제 시 남은 노드들의 배치 유지 (자동 재정렬 없음)
- [x] 엣지 삭제도 서버 성공 후에만 로컬 반영 + 분리된 서브트리 색 재계산(§6)

## 10. 서버 계약 (검증된 동작)

클라이언트가 의존하는 서버 동작. **문서와 코드가 다르면 코드가 진실** — 서버 레포 `../server`(Won-Life/Aideep_backend)로 검증한다.

- **WS broadcast는 발신자 제외** — per-user 룸 `.to(workspaceId).except(userRoom(userId))` (Aideep_backend#47). 본인 이벤트는 원래 돌아오지 않으므로 클라의 `currentUserId` 필터는 서버 회귀·룸 join 어긋남 대비 안전망.
- **`PATCH /workspace/:id/node/:id/move`**: 대상 노드를 절대 좌표로 저장하면서 **DB 기준 delta를 모든 자손에게 전파**(edge 기반 재귀 CTE, 색 경계 무시). 응답은 `{nodeId, x, y}`, depth 불포함.
- **`PATCH /workspace/:id/node/:id`** (`updateNodeMeta`): `{title, color, textColor, propagateToChildren, nodeType}`. `propagateToChildren` + color 변경 시 색 경계 없이 전 자손 덮어쓰기(Aideep_backend#51) — 클라는 이 옵션을 쓰지 않고 노드별 PATCH로 대체. nodeType 변경 시 WS `NODE_UPDATE` broadcast.
- **`PATCH /workspace/:id/edge/:edgeId`** (`updateEdge`): `source_handle`/`target_handle`만 수정, WS `EDGE_UPDATE` broadcast (Aideep_backend PR #59).
- **`createEdge`(`connectNodes`) 서버 검증**: self-loop·중복 엣지·역방향 엣지·target=PROJECT 노드·**순환(`hasCycle` BFS)**을 서버가 거부한다. **미검증: 크로스 그래프(색)·단일 부모** — 이 둘만 UI 레벨(§3-2)에서 막는다.
- **depth**: 서버 `propagateDepth`가 엣지 생성·삭제 시에만 갱신하고, 갱신값을 WS·REST 응답에 싣지 않는다. `deleteNode`는 depth를 전파하지 않는다(Aideep_backend#64). 따라서 클라가 엣지 상태 변경 지점마다 `applyDepthOnEdgeCreate/Delete`로 서버 규칙을 미러링한다(`src/features/graph/CLAUDE.md`).
- **노드 sync/read DTO 필드**: `node_id, title, node_type, content(색·textColor 포함), version, position_x/y, depth, workspace_id, 타임스탬프`. `handleSide`·`isMain`은 서버에 없음 — handleSide는 엣지 핸들에서 재유도, isMain은 `node_type === 'PROJECT'`로 파생.
- **`deleteNode`**: 노드는 soft-delete, 그 노드에 연결된 엣지는 hard-delete(`deleteEdgesByNodeId`).
- **메인 노드 색 필수 (Aideep_backend#52, PR #60)**: PROJECT 노드 생성 시 `color`/`textColor` 필수. 기존 색 미저장 노드는 백필 SQL(`docs/migrations/2026-07-13-backfill-project-node-color.sql`)로 채움 — 적용 후 클라의 색 추정 폴백·`backfillMainColor`는 제거 가능(§11-미해결).

## 11. 설계 결정 · 미해결 과제

동작 서술이 아니라, **왜 이렇게 했는가(설계)**와 **아직 안 된 것(미해결)**이다. 동작을 바꾸는 결정이 내려지면 본문과 함께 이 절을 갱신한다.

### 설계 결정

**크로스 그래프 연결 차단이 의도된 동작.** 서로 다른 그래프(색) 노드를 잇는 엣지는 이동·색 전파·삭제 캐스케이드를 그래프 경계 너머로 번지게 하고, depth≠0 루트 같은 데이터 꼬임을 낳는다([Aideep_backend#64](https://github.com/Won-Life/Aideep_backend/issues/64) 논의). 핸들 드래그가 크로스 그래프 엣지의 유일한 신규 발생 경로였으므로 `isValidConnection`이 색 비교로 원천 차단한다(§3-2). 나머지 연결 경로(노드 드래그 편입·리소스 드롭·빈 공간 드롭)는 상대를 자기 그래프로 편입(재색칠)하므로 크로스 엣지를 만들지 않는다. 이에 따라 노드에 그래프 uuid를 영속화하려던 graphId 도입 설계([AiDeep-web#133](https://github.com/Won-Life/AiDeep-web/issues/133))는 폐기됐다. 서버 `createEdge`는 색을 검사하지 않으므로(§10) 이 차단은 UI 레벨이며, DB에 남은 legacy 크로스 엣지는 대칭 이동 시 절단(`findCrossColorChildEdges`)이 청소 안전망.

**색상을 그래프 경계로 쓰는 이유.** 크로스 그래프 연결이 차단되면 "엣지로 연결된 집합 = 한 그래프"가 되지만, DB에 남은 legacy 크로스 엣지 때문에 순회가 경계를 넘을 수 있다. 색의 남은 역할은 두 가지 — ① 연결 게이트의 그래프 정체성 비교(§3-2, 같은 색 = 같은 그래프), ② legacy 크로스 엣지 방어(`getSameColorDescendantIds`가 색 경계에서 순회를 멈춤). 알려진 트레이드오프: 두 그래프가 우연히 같은 색이면 연결 게이트가 둘을 같은 그래프로 취급해 병합을 허용한다(크로스 엣지가 없으면 이동·전파·삭제가 번질 경로는 없음).

**조상·형제 재부모화 허용.** 노드 드래그 편입(§3-5)은 순환만 차단하고(§3-2) 같은 그래프 내 조상·형제로의 스냅은 허용한다 — 마인드맵 트리에서 노드를 다른 부모 밑으로 옮기는 정상 편집 조작이며, 순환도 단일 부모 위반도 아니다.

**다중 선택 드래그는 색 경계를 무시.** shift+클릭·박스 선택으로 2개 이상 고른 노드는 그래프 소속과 무관하게 전체 서브트리(`getDescendantIds`)를 함께 옮기고 그 위치를 서버에 저장한다(§5-1·§5-3). 사용자가 손으로 명시적으로 고른 노드들이므로 그룹 이동이 맞다 — "단일 드래그는 다른 그래프가 안 따라옴"과는 별개 제스처의 별개 규칙(모순 아님).

**형제·조상 연결 차단은 부수 효과.** "형제·부모·조상과 연결 불가"는 전용 검사가 없다. 직접 부모-자식만 명시 차단이고, 나머지는 같은 그래프 검사(depth 0 루트 공유)와 단일 부모 검사의 부수 효과로 성립한다(§3-2).

### 미해결 과제

- **드래그 중 협업자 이동이 내 화면에서 되돌아감**: 드래그 중 d3 tick이 d3 라이브 좌표로 전 노드를 매 프레임 덮어쓰는데, 협업자의 WS 이동은 React state에만 반영되고 d3 좌표엔 안 들어가 다음 tick에 옛 위치로 복귀. 드래그 종료 후에도 다시 그릴 계기가 없어 다음 WS 이벤트·새로고침 전까지 어긋난다 (§5-3).
- **밀려난 주변 노드 위치 미저장**: 시뮬레이션에 밀려나기만 한(드래그 대상 아닌) 노드는 저장하지 않아 새로고침 시 원위치 복귀 — 그 사이 내 화면·DB·협업자 화면이 서로 다르다 (§5-3).
- **opt/alt 단독 이동 보정 왕복**: 서버 move 전파가 (안 움직인) 자식들을 delta만큼 밀어버려 종료 시 자식 수만큼 원위치 복원 PATCH가 나간다. 대칭 이동도 왕복이 자손 수에 비례 — 성능 개선 여지 [AiDeep-web#143](https://github.com/Won-Life/AiDeep-web/issues/143).
- **depth 서버 수신값 적용 대기**: 현재는 클라가 `applyDepthOnEdgeCreate/Delete`로 서버 `propagateDepth`를 미러링한다. 서버가 갱신값을 WS·REST에 실어주면([Aideep_backend#63](https://github.com/Won-Life/Aideep_backend/issues/63)) 수신값 적용으로 교체. 또한 서버 `deleteNode`가 depth를 전파하지 않아(#64) 노드 삭제로 부모를 잃은 root가 depth≠0으로 남는 공백이 있다.
- **legacy 데이터 정리 후 단순화**: 색 미저장 legacy 메인 노드는 색 비교를 통과할 수 있고(백필 마이그레이션 적용 후 해소), legacy 크로스 엣지가 데이터 차원에서 정리되면 색 경계 순회(`getSameColorDescendantIds`)를 단순 자손 순회(`getDescendantIds`)로 대체할 수 있다. 이때 `backfillMainColor`와 색 추정 폴백도 제거 가능.
