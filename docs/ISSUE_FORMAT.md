# GitHub 이슈 기본 포맷

이슈를 생성하는 사람(사람·AI 모두)은 아래 구조를 기본으로 사용한다.
확정 사례: [Aideep_backend#55](https://github.com/Won-Life/Aideep_backend/issues/55) — 이 구조로 개정한 뒤 표준으로 채택됨.

## 원칙

독자는 이 이슈를 만들게 된 대화·맥락을 전혀 모르는 사람이다 (예: 프론트 상태를 모르는 백엔드 개발자, 미래의 나).

1. **제목에 작업 항목 나열 금지** — "컬럼·API·WS 페이로드·백필" 같은 나열은 암호문이다. "무엇을 왜"를 평문으로 쓰고, 괄호에 작업 요약을 붙인다.
   - ❌ `노드에 graph_id 추가 — 컬럼·API·WS 페이로드·기존 데이터 백필`
   - ✅ `노드가 어느 그래프 소속인지 식별하는 graph_id 도입 (새 컬럼 + API/WS 반영 + 기존 데이터 채우기)`
2. **대화 중 만든 축약어·조어 금지** — 정의 없이 쓴 조어가 하나라도 있으면 실패. 풀어 쓴다.
3. **관찰 가능한 증상 포함** — 콘솔 에러 메시지, 화면에서 보이는 현상 등 독자가 자기 환경에서 대조할 수 있는 구체물.
4. **라벨 필수** — 생성 전 `gh label list -R {repo}` 확인 후 최소 1개 부착.
5. **관련 이슈 상호 링크** — 선행 조건·파생 이슈는 본문에서 서로 가리킨다.

## 본문 스켈레톤 (순서 고정)

```markdown
> **요약**: 배경 지식 없는 독자가 이 문단만 읽어도 "무엇을 왜 해달라는지"
> 파악되도록 3~4문장. 현재 동작 → 문제 → 요청을 한 호흡에.

### 전제 (독자가 모르는 시스템 동작)

1. 번호 목록. 이 이슈가 성립하는 배경 동작(데이터 흐름·동기화 구조)을
   위에서 아래로만 읽어도 따라오게 깐다.

### 문제

**1. 소제목 (분류: 성능 / 정확성 / 선행 조건 등)**

항목별로 굵은 소제목을 달고, 관찰 가능한 증상은 **굵게** 표시한다.

### 요청 사항

작업 덩어리 개요 문장을 먼저 깔고 ("작업은 네 덩어리다: ① … ② …"),
번호 목록으로 상세화한다. 각 항목에 "왜 필요한지" 부연을 붙인다.

### 결정 근거 (대안 비교)

- 검토했던 대안 → 기각 사유
```

## 유형별 조정

- **버그 리포트**: `### 문제` 대신 `### 재현 절차` + `### 기대 동작 / 실제 동작`. 라벨 `bug`.
- **기능 요청**: 위 스켈레톤 그대로. 라벨 `enhancement`.
- **타 레포에 보내는 요청** (예: 클라 → 백엔드): 전제 섹션에 상대가 모르는 우리 쪽 동작을 반드시 깐다.
