# 일반 노드 → 프로젝트(중심) 노드 전환 — 설계 노트

> 상태: **설계 중(미구현)**. 브랜치 `feat/project-node-conversion`.
> 이 문서는 이 대화를 못 본 사람(미래의 나 포함)이 읽는다는 전제로 쓴다.

## 용어 정의

- **중심 노드(= "프로젝트 노드")**: 한 그래프의 최상위 기준 노드. 서버에선 `node_type = 'PROJECT'`, 클라이언트에선 `data.isMain = true`로 표현. 헤더의 프로젝트 chip 목록은 이 `isMain` 노드들을 나열한다.
- **일반 노드**: `node_type = 'DATA'` (그 외 `RESOURCE`, `ARCHIVE`도 있음).
- **depth**: 트리 루트로부터의 거리(부모 depth + 1). 루트는 depth 0.
- **부모 / 자식**: 엣지 방향으로 정해진다. 엣지 `source_id → target_id`에서 source가 부모, target이 자식.
- **그래프**: 색(`data.color`)으로 구분되는 노드 집합. 서버엔 그래프 ID가 없고, 색이 그래프 경계다.

## 전제 (현재 시스템 동작) — 서버 코드로 검증함

서버 레포 `../server`(Won-Life/Aideep_backend) 실제 코드 기준. 문서가 아니라 코드로 확인한 사실이다.

1. **서버엔 `isMain` 개념이 없다.** 중심 노드 = `node_type_enum.PROJECT`. `depth`는 별개 컬럼(`prisma/schema.prisma:39,46`).
2. **서버는 중심 노드 단일성을 강제하지 않는다.** `PROJECT` 노드는 몇 개든 만들 수 있다. 스키마 유니크 제약도, 서비스 체크도 없다(`node.service.ts createProjectNode`).
3. **노드 타입 변경 = 범용 PATCH 한 컬럼 수정.** `PATCH /workspace/:wsId/node/:nodeId`(`updateNodeMeta`)에 `nodeType`을 넘기면 대상 노드의 `node_type`만 바꾸고 협업자에게 `NODE_UPDATE`로 방송한다. **depth 재계산·기존 PROJECT 강등·엣지 변경·자식 전파를 일절 하지 않는다**(`node.service.ts:251-255`).
4. **depth는 오직 엣지 생성/삭제 시에만 자동 갱신된다**(`propagateDepth`, `edge.service.ts:119-124,170-175`). depth를 직접 세팅하는 API는 없다.
   - 생성: target과 그 자손 전체 `depth += source.depth + 1`
   - 삭제: target과 그 자손 전체 `depth -= target.depth` (target은 0으로)
5. **엣지 방향을 바꾸는 API가 없다.** 엣지 PATCH는 `sourceHandle`/`targetHandle`(핸들 위치)만 수정한다. 방향(source↔target) 변경은 **삭제 후 재생성**뿐이다(`edge.service.ts:192-226`).
6. **PROJECT 노드는 엣지의 target이 될 수 없다.** 서버가 `target.node_type === 'PROJECT'`이면 연결을 거부한다(`edge.service.ts:93`). 즉 중심 노드는 부모를 가질 수 없고 항상 부모(source)로만 존재한다.
7. **단일 부모 불변식도 서버가 강제하지 않는다.** 한 노드가 서로 다른 두 부모의 자식이 되는 것을 막지 않는다. 클라이언트 UI 레벨에서만 유지한다(#92).
8. **클라이언트는 depth를 로컬로 미러링한다.** 서버가 갱신한 depth를 WS·REST 응답에 싣지 않으므로, 엣지가 바뀌는 모든 지점에서 `applyDepthOnEdgeCreate/Delete`(`graphUtils.ts`)로 서버와 동일 규칙을 다시 계산한다.

## 현재 동작과 관찰 가능한 증상

지금 우클릭 "프로젝트 노드로 변경"은 `handleToggleNodeType`(`GraphCanvas.tsx:1294`)에서 **대상 노드의 `isMain`/`nodeType`만 뒤집고 nodeType을 PATCH**할 뿐이다. 그래서:

- **증상 1 — 중심 노드가 여러 개가 된다.** 이미 프로젝트 노드가 있는 그래프에서 다른 노드를 프로젝트로 바꾸면 둘 다 `isMain`이 되고, **헤더에 프로젝트 chip이 2개** 뜬다.
- **증상 2 — 승격한 노드가 여전히 부모 밑에 매달려 있다.** 부모 엣지가 그대로라 새 "중심"이 트리 중간에 있고, depth도 0이 아니다.
- **증상 3 — depth가 실제 구조와 어긋난다.** nodeType만 바꿔 depth를 안 건드리므로 루트/대칭축/같은-그래프 판정(모두 depth 0 기준, #99·#146)이 오염된다.

## 처리해야 할 문제 목록

전환을 제대로 하려면 클라이언트가 아래를 순서대로 오케스트레이션해야 한다. 서버가 대신 해주는 건 3·6번 항목의 저수준 연산뿐이다.

- **P1. 기존 중심 노드 강등.** 같은 그래프(색)에 이미 있는 `PROJECT` 노드를 찾아 `DATA`로 PATCH. 서버가 단일성을 안 지키므로(전제 2) 클라이언트가 직접 내려야 한다. — 엣지 케이스: 대상 노드가 엣지 0개 단독 노드면 같은 그래프에 기존 중심이 없을 수 있다(강등 생략).

- **P2. 재루팅(부모 엣지 방향 뒤집기).** 승격할 노드 X가 부모 체인(옛 루트 R … → P → X) 밑에 있으면, X를 루트로 만들기 위해 **X에서 옛 루트까지의 경로에 있는 엣지만** 전부 방향을 뒤집는다. 그러면 조상들이 X의 자손이 된다. X의 기존 자식들은 그대로 둔다. 방향 변경 API가 없으므로(전제 5) 경로상의 각 엣지를 **삭제 후 반대 방향으로 재생성**한다.
  - 경로 전체를 일관되게 뒤집어야 다중 부모가 안 생긴다(전제 7): P의 옛 부모 엣지 `GP→P`도 `P→GP`로 같이 뒤집어야 P의 부모가 X 하나로 유지된다. 경로 일부만 뒤집으면 P에 부모가 2개가 된다.

- **P3. depth 재계산.** PATCH nodeType은 depth를 안 건드린다(전제 3). depth는 엣지 삭제/재생성이 유발하는 `propagateDepth`로만 바뀌는데(전제 4), 재루팅은 여러 엣지를 지웠다 다시 만들어 **중간 상태의 depth가 순서에 의존**한다. 클라이언트 미러(전제 8)가 서버와 정확히 일치하도록 순서를 설계하거나, 아래 "열린 결정"의 서버 엔드포인트로 원자화해야 한다.

- **P4. PROJECT-as-target 제약 준수.** X를 `PROJECT`로 만들면 X로 들어오는 엣지가 있으면 안 된다(전제 6). 재루팅이 끝나면 X는 나가는 엣지만 남으므로 충족되지만, **작업 순서**가 중요하다: 부모 엣지를 먼저 정리(재루팅)한 뒤 X를 `PROJECT`로 승격해야, 재생성 단계에서 "PROJECT로 들어오는 엣지" 거부에 걸리지 않는다.

- **P5. 핸들 방향 정규화(React Flow #008).** 엣지 방향이 바뀌면 관련 노드의 `handleSide`와 엣지 핸들을 새 방향으로 갱신·저장해야 한다. 누락 시 새로고침 후 부모·자식 엣지 핸들이 모순되어 엣지가 렌더링에서 탈락한다. 기존 서브트리 방향 전환 기계(`subtreeInternalEdgeFilter`·`persistSubtreeEdgeHandles`, graph CLAUDE.md 참고)를 재사용할 수 있는지 검토.

- **P6. 색/표시.** 중심 노드는 흰색 표시 + 색 저장 규칙이 있다(isMain 규칙). 강등·승격 시 색 처리 확인.

- **P7. 원자성·롤백.** 위는 전부 개별 REST 호출(강등 PATCH → 엣지 N개 삭제/생성 → 승격 PATCH)이고 **서버 트랜잭션이 없다.** 중간에 하나 실패하면 그래프가 반쯤 전환된 상태로 남는다(협업자에게도 중간 상태가 방송됨). 실패 지점까지 되돌리는 롤백 전략 또는 "새로고침 sync로 수렴" 허용을 결정해야 한다.

- **P8. 협업 동기화.** 각 단계가 독립 WS 이벤트로 방송되어 협업자는 전환 과정을 조각조각 본다. 낙관적 반영 순서와 협업자 화면의 일관성 확인.

- **P9. 역방향 시나리오(중심 노드가 없는 그래프에서 새로 만들기).** 프로젝트 노드가 하나도 없을 때 X를 승격하면 P1(강등)만 없고 P2~P5는 동일하다. X를 depth 0으로 놓고 그래프 전체 depth를 X 기준으로 재정렬.

## 열린 결정 (구현 전에 정해야 함)

- **D1. 서버에 원자적 "중심 노드 지정" 엔드포인트를 신설할지.** P1~P4·P7을 클라이언트가 다단계로 흉내 내는 대신, 서버가 한 트랜잭션에서 (기존 PROJECT 강등 + 재루팅 + depth 재계산)을 처리하면 원자성·순서·미러링 문제가 통째로 사라진다. **백엔드 이슈로 제안 권장** — 클라 단독 구현은 P3·P7 리스크가 크다.
- **D2. depth 재계산 방식.** (a) 엣지 삭제/생성 순서를 설계해 `propagateDepth`가 올바른 depth를 만들게 하고 클라가 미러 / (b) 새로고침 sync가 서버값으로 수렴하도록 허용(전환 직후 잠깐 어긋남 감수) / (c) D1의 서버 엔드포인트.

## 사용자 안내 문구 후보

기존 중심 노드가 있는 그래프에서 승격할 때만 확인 모달을 띄운다(기존 중심이 교체되므로). "프로젝트 노드"·"depth"·"루트" 같은 내부 용어를 쓰지 않고 **"중심"** 하나로 설명한다.

- **후보 A (간결):**
  - 제목: `이 노드를 그래프의 중심으로 바꿀까요?`
  - 본문: `지금은 '{기존중심제목}'이(가) 이 그래프의 중심이에요. 바꾸면 기존 중심은 일반 노드가 되고, 연결 관계가 이 노드를 기준으로 다시 정리돼요.`
  - 버튼: `중심으로 바꾸기` / `취소`

- **후보 B (결과 강조):**
  - 제목: `그래프의 중심을 옮길까요?`
  - 본문: `한 그래프에는 중심이 하나만 있을 수 있어요. 이 노드를 중심으로 만들면 '{기존중심제목}'은(는) 일반 노드로 바뀌고, 위아래 연결 방향이 이 노드 기준으로 다시 맞춰져요.`
  - 버튼: `중심으로 옮기기` / `취소`

두 후보 모두 실제 문구는 구현 시점에 UI_GUIDE·디자인과 맞춰 확정.
